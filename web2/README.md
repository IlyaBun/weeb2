# Система оценки успеваемости ПолесГУ

## Назначение

Небольшое PHP-приложение для учета студентов, дисциплин, оценок и просмотра агрегированной аналитики. Приложение построено как монолит без фреймворка: серверная логика, HTML-шаблоны и часть JavaScript находятся в одном проекте, данные хранятся в SQLite.

Документ нужен как рабочая карта проекта для дальнейшего развития: добавления новых модулей, API-методов, форм и отчетов.

## Технологический стек

- PHP с встраиваемыми шаблонами
- SQLite через PDO
- Frontend без сборки: обычный HTML, CSS, JavaScript
- Внешние CDN-зависимости: Chart.js, SweetAlert2, Font Awesome, Google Fonts
- Встроенный PHP-сервер для локального запуска

## Быстрый запуск

### Вариант 1. Через встроенный PHP-сервер

Из корня проекта:

```powershell
php -S localhost:8000
```

После запуска открыть:

```text
http://localhost:8000/login.php
```

### Вариант 2. Через `start.bat`

В проекте есть `start.bat`, но сейчас он жестко привязан к путям:

- `C:\web2`
- `C:\xampp\php\php.exe`

Это значит, что bat-файл сработает только в конкретной локальной конфигурации. Для переносимого запуска лучше использовать команду `php -S localhost:8000` из текущей директории.

## Общая архитектура

Приложение построено вокруг одной основной точки входа:

- `login.php` отвечает за аутентификацию
- `index.php` отвечает за авторизованную зону и маршрутизацию по модулям
- `logout.php` завершает сессию

После логина пользователь попадает в `index.php`, где по `$_GET['module']` подключается нужный модуль из папки `modules`.

### Схема потока запроса

1. Пользователь открывает `login.php`.
2. После успешной проверки пары `login/password` в таблице `users` создается PHP-сессия.
3. Пользователь переходит в `index.php`.
4. `index.php` подключает `config/database.php` и `config/functions.php`.
5. По параметру `module` подключается соответствующий файл из `modules/*/index.php`.
6. Модуль сам обрабатывает `GET` и `POST`, читает/пишет данные в SQLite и рендерит HTML.
7. Общие layout-файлы подключаются через `includes/header.php`, `includes/sidebar.php`, `includes/footer.php`.

## Модель данных

База создается автоматически при первом вызове `getDB()` в `config/database.php`.

### Таблицы

#### `users`

- `id`
- `login` уникальный
- `password`
- `role` (`admin` или `teacher`)
- `full_name`

Используется для входа и разграничения доступа.

#### `groups`

- `id`
- `name`
- `course`
- `specialty`

Справочник учебных групп.

#### `students`

- `id`
- `group_id` -> `groups.id`
- `full_name`
- `birth_date`
- `status` (`active` или `expelled`)

Удаление в UI реализовано как мягкое: студенту ставится `status = 'expelled'`.

#### `disciplines`

- `id`
- `name`
- `teacher`
- `department`
- `hours`

Справочник дисциплин.

#### `grades`

- `id`
- `student_id` -> `students.id`
- `discipline_id` -> `disciplines.id`
- `grade` от 1 до 10
- `date`
- `type` (`exam` или `credit`)

Хранит историю всех выставленных оценок. Обновления существующих записей нет, журнал работает как добавление новых строк.

### Связи

- одна группа -> много студентов
- один студент -> много оценок
- одна дисциплина -> много оценок
- один пользователь -> бизнес-связями не связан, используется только для авторизации

## Инициализация данных

При первом запуске приложение:

1. создает таблицы SQLite
2. генерирует тестовых пользователей
3. создает группы и дисциплины
4. генерирует 165 студентов
5. генерирует стартовый массив оценок

Это удобно для демо, но важно помнить: схема и seed логика смешаны с runtime-кодом в `config/database.php`.

## Серверные слои и ответственность

### `config/database.php`

Отвечает за:

- singleton-подключение к SQLite через `getDB()`
- первичную инициализацию базы `initializeDatabase()`
- генерацию тестовых данных `generateTestData()`
- базовые функции авторизации и агрегатов, например `calculateStudentAverage()`

Это не только инфраструктурный файл, но и место, где сейчас лежит часть доменной логики.

### `config/functions.php`

Отвечает за:

- экранирование и форматирование (`escape`, `formatDate`)
- UI-хелперы оценок (`getGradeText`, `getGradeColor`)
- аналитические запросы (`getRiskStudents`, `getExcellentStudents`, `getRecentGrades`, `getGradeDistribution`, `getGroupRating`, `getMonthlyDynamics`)
- справочники (`getAllGroups`, `getAllDisciplines`, `getStudentsByGroup`, `getStudentGrades`)

Если добавляется новая аналитика или повторно используемый серверный helper, логично начинать именно здесь.

## Модули

### Dashboard

Находится прямо в `index.php`, а не в отдельной папке.

Показывает:

- общее число активных студентов
- средний балл факультета
- число отличников
- число студентов группы риска
- качество знаний
- распределение оценок
- рейтинг групп
- помесячную динамику
- последние оценки

Для графиков PHP подготавливает массивы и прокидывает их в глобальные JavaScript-переменные через `$additionalScripts`.

### `modules/students`

Функции:

- список студентов
- фильтр по группе
- поиск по ФИО
- добавление студента
- редактирование студента
- мягкое удаление через `status = 'expelled'`
- просмотр карточки студента через AJAX-запрос в `api/student.php`

Особенность: средний балл считается отдельно для каждого студента в цикле, что при росте объема данных может стать узким местом.

### `modules/disciplines`

Функции:

- список дисциплин
- добавление
- редактирование
- физическое удаление

Особенность: при удалении дисциплины связанные оценки будут удаляться каскадно на уровне внешнего ключа.

### `modules/grades`

Функции:

- выбор группы и дисциплины
- загрузка активных студентов выбранной группы
- массовое сохранение оценок

Особенность текущей реализации:

- модуль только добавляет новые записи в `grades`
- редактирования уже существующих оценок нет
- при сохранении используется транзакция

### `modules/analytics`

Функции:

- фильтрация по группе
- фильтрация по дисциплине
- метрики успеваемости
- качество знаний
- средний балл
- список должников
- круговая диаграмма распределения
- печать страницы через `window.print()`

### `modules/users`

Доступен только администратору.

Функции:

- создание пользователя
- изменение ФИО и роли
- смена пароля
- удаление пользователя

Правило безопасности в текущей реализации: нельзя удалить самого себя.

## API

### `GET /api/student.php?id={id}`

Возвращает JSON:

- `student` — данные студента и группы
- `grades` — список оценок студента
- `avg_grade` — средний балл

Требует активной сессии. Используется модулем студентов для модального окна карточки.

Содержит:

## Авторизация и права доступа

Механизм доступа построен на `$_SESSION`.

После успешного логина в сессию сохраняются:

- `user_id`
- `login`
- `role`
- `full_name`

Проверка доступа выполняется в двух стилях:

- вручную через `session_start()` и `isset($_SESSION['user_id'])` внутри файлов
- через вспомогательные функции `checkAuth()` и `checkAdmin()` в `config/database.php`

На практике модули используют в основном ручную проверку, а не единый middleware-подход.

## Типовые сценарии изменений

### Добавить новый модуль

1. Создать папку `modules/<module_name>/`.
2. Добавить `index.php` по образцу существующих модулей.
3. Подключить `config/database.php` и `config/functions.php`.
4. Реализовать обработку `GET/POST` прямо в модуле.
5. Добавить пункт меню в `includes/sidebar.php`.
6. Добавить новый case в роутер `index.php`.

Пример маршрута:

```php
case 'attendance':
    require __DIR__ . '/modules/attendance/index.php';
    break;
```

### Добавить новый API-эндпоинт

1. Создать файл в папке `api/`.
2. В начале файла проверить сессию.
3. Подключить `database.php` и `functions.php`.
4. Вернуть JSON через `json_encode()`.
5. Использовать `fetch()` из модуля или общего JS.

### Добавить новую сущность в БД

Сейчас миграций нет, поэтому есть два пути:

1. Изменить схему в `initializeDatabase()` и пересоздать БД.
2. Написать отдельный одноразовый SQL-скрипт миграции.

Для дальнейшего развития предпочтителен второй путь, иначе любое изменение схемы будет неудобно применять на существующей базе.

### Добавить новый отчет или KPI

Рекомендуемый путь:

1. Вынести SQL-логику в `config/functions.php`.
2. Вызвать функцию в нужном модуле.
3. Передать данные в шаблон.
4. Если нужен график, сериализовать данные через `json_encode()` и инициализировать Chart.js.

## Практические соглашения проекта

- Один модуль = один `index.php`, в котором одновременно живут обработка запроса и HTML.
- Повторно используемые SQL-хелперы лучше складывать в `config/functions.php`.
- Общий layout подключается через include-файлы.
- UI-уведомления строятся на SweetAlert2.
- Для таблиц и карточек используется единая стилистика из глобального CSS.
- Большинство действий выполняются через обычные POST-формы, а не через полноценный SPA/API-подход.

## Текущие ограничения и технический долг

Это особенно важно учитывать перед добавлением новых фич.

### 1. Хранение паролей в открытом виде

Пароли сравниваются напрямую в `login.php` и хранятся в таблице `users` без хеширования. Перед внедрением реальной эксплуатации нужно перейти на `password_hash()` и `password_verify()`.

### 2. Нет CSRF-защиты

POST-формы не используют CSRF-токены. Для внутренних демо это терпимо, для реальной системы нет.

### 3. Часть SQL собирается строкой

Например, в аналитике есть запросы, где фильтры подставляются в строку вручную. Сейчас значения приводятся к integer, но для новых запросов лучше везде придерживаться prepared statements.

### 4. Смешение ответственности

В проекте нет четкого разделения на controller/service/repository/view. Это ускоряет разработку небольших фич, но усложняет сопровождение.

### 5. Нет миграций

Схема БД создается автоматически при старте, а механизм обновления уже существующей базы отсутствует.

### 6. Дублирование проверки авторизации

Проверки сессии размазаны по файлам. Если добавлять много новых модулей, стоит централизовать доступ через один helper.

### 7. Производительность на росте данных

Некоторые вычисления делаются по одному запросу на запись или сущность. Для тестовых объемов это нормально, для больших наборов данных потребуется агрегирование в SQL.

### 8. `start.bat` зависит от локальных путей

Файл запуска в текущем виде не является переносимым.

## Что стоит стабилизировать перед крупными новыми фичами

Если планируется активное развитие проекта, полезно сначала сделать базовый технический каркас:

1. Вынести auth-проверки в единый helper и использовать его везде.
2. Перевести пароли на безопасное хеширование.
3. Ввести простой механизм миграций SQLite.
4. Перенести крупные SQL-запросы и бизнес-логику из модулей в отдельные функции.
5. Постепенно заменить inline JavaScript модулей на отдельные файлы или хотя бы на единый namespace.

## Рекомендованный шаблон для новой фичи

Если нужно добавить новую функцию без крупной переработки архитектуры, лучше придерживаться существующего стиля:

1. Определить новую сущность или новый use case.
2. Если нужны данные из БД, добавить helper-функцию в `config/functions.php`.
3. Если требуется отдельный экран, создать новый модуль в `modules/`.
4. Если нужен AJAX, добавить endpoint в `api/`.
5. Подключить экран в роутере `index.php` и в меню `includes/sidebar.php`.
6. Использовать существующие CSS-классы карточек, таблиц, форм и модалок, чтобы не плодить новый UI-слой.

## Краткая карта файлов, которые чаще всего придется менять

- Новый раздел в меню: `includes/sidebar.php`
- Новый маршрут: `index.php`
- SQL и переиспользуемая серверная логика: `config/functions.php`
- Изменение схемы/seed: `config/database.php`
- Общие UI-поведения: `assets/js/main.js`
- Общие стили: `assets/css/style.css`
- JSON для модалок/динамики: `api/*.php`
- Экран бизнес-функции: `modules/<module>/index.php`

## Итог

Сейчас это компактный монолит на PHP + SQLite, удобный для быстрых доработок внутри одной команды. Для добавления новых фич важнее всего помнить три вещи:

- все проходит через `index.php` и модульные `index.php`
- общие SQL-хелперы уже частично вынесены в `config/functions.php`
- проект прост в расширении, но перед серьезным ростом ему потребуется минимальная техническая стабилизация
